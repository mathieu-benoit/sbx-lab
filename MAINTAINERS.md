# Maintainer notes (not for participants or agents)

This repository is the **Docker Sandboxes with GitHub Copilot Lab**: a guided lab (`README.md` and `instructions/`) built around the DevBoard sample app in `project/`. The agent guidance for the sample app itself lives in [`project/AGENTS.md`](project/AGENTS.md) and the root [`AGENTS.md`](AGENTS.md).

## Rules

- **Never `git push` without explicit user confirmation.** Stage and commit when asked, then stop and ask before pushing.

## Keeping the lab working

- The lab depends on the app's **intentional bugs**. Do not "fix" them in `main`: pagination (`backend/app/routers/issues.py`), `updated_at` (`backend/app/models.py`), search (501) and the notification stub. See [`project/README.md`](project/README.md#known-issues).
- Expected baseline of `cd project/backend && pytest -v`: **3 failed, 12 passed, 1 xfailed**. The `project-ci` workflow checks exactly which tests fail.
- After the exercises are completed, all tests pass (15 passed, plus the search test).
- Dependency bumps (Dependabot) are the main risk: check that `project-ci` is green, and run the whole lab once before each session.

## `sbx` CLI facts (checked against `sbx` v0.54 and the [docs](https://docs.docker.com/ai/sandboxes/))

- `sbx create` requires an explicit workspace path: `sbx create --name=foo claude .`
- `sbx run` infers the current directory: `sbx run claude`. Reconnect to an existing sandbox with `sbx run --name <sandbox-name>`.
- Clone mode (`--clone`) exposes the clone as the Git remote `sandbox-<name>` (branches `sandbox-<name>/<branch>`). Since v0.54 the remote goes through the daemon socket (`remote.<name>.uploadpack` runs `sbx upload-pack`), not a localhost TCP port: tested on Windows. Stopping the sandbox removes the remote and its tracking branches (`git fetch` then fails with `does not appear to be a git repository`); starting it again restores them. Fetched commits are mirrored to `refs/sandboxes/<name>/*`, which survive `sbx rm`.
- Multiple workspaces: the first path is the primary one (read-write); extra paths can be appended with `:ro` for read-only.
- `sbx policy` subcommands: `allow`, `deny`, `check`, `init`, `log`, `ls`, `reset`, `rm` (also `approval`, `inspect`, `profile`, `refresh`). Non-interactive reset: `sbx policy reset --force && sbx policy init deny-all` (or `balanced`).
- The lab runs with the **deny-all** policy plus the allow list in module 01 (*Allow only what the lab needs*). It was derived from `sbx policy log` of a full run (Copilot Enterprise; `**.githubcopilot.com` also covers the Individual and Business subdomains). If the lab starts using a new host (dependency, image, registry), add it there. A full run of modules 06-09 under this policy (`sbx` v0.53.0, Copilot Enterprise) had no blocked hosts other than Next.js telemetry, which Compose now disables.
- Secrets are global by default; use `--sandbox <name>` to scope one. Global secrets are injected at sandbox creation time.
- Copilot starts with `--yolo` by default; arguments after `--` are appended.
- Services must listen on `0.0.0.0` (not `127.0.0.1`) for port forwarding to work.
- `host.docker.internal` reaches host services from inside a sandbox.
- `SBX_NO_TELEMETRY=1` disables telemetry.

## MCP module (checked with `sbx` v0.53.0)

- Remote MCP servers (`--url https://...`) work in local sandboxes and can be loaded live with `sbx mcp load NAME --sandbox SANDBOX`; their tools show up directly in the agent's tool list. Module 10 creates a dedicated `mcp` sandbox with `--static-mcp dhi` (gateway with exactly that server and no discovery tools): tested end to end. Loading into a `--static-mcp none` sandbox with `sbx mcp load` also works.
- Image servers (`--url dhi.io/fetch-mcp:latest`) did not work: `sbx mcp load` fails with `409 ... has no control-plane MCP gateway; cannot add a remote server live`, and with `--static-mcp` the gateway starts with no backend. `--local` and `--command docker ...` servers need Docker on the host, which the lab doesn't require. Hence the remote DHI server in module 10.
- The DHI MCP server also exposes write tools (`dhi_create_mirror`, `dhi_remove_mirror`); the module's prompt only asks for look-ups and for the list of tools called (in the test, the agent used only `dhi_get_tag_definition` and `dhi_get_repository`).
- Registration with a fresh account (`sbx mcp add dhi --url https://dhi.io/mcp`, browser sign-in) was not re-tested: the test machine already had it registered.

## Kits module (checked with `sbx` v0.53.0)

- Module 02 (right after the network policies) shows `sbx kit inspect sbx/copilot` (table and `--format yaml`) and compares with `sbx/claude`. The sample outputs include image digests, which change when the kits are updated.
- The `sbx` CLI shows agent kits as `kind: sandbox` with a `sandbox:` block (image, entrypoint, command), while the [kit specification](https://github.com/docker/sandbox-kit-spec) repository describes `workload` and `mixin` kits with `capabilities:`. Agent kits are shown the way `sbx` prints them; the Python mixin uses the specification's format (`kind: mixin`, `capabilities:`), which `sbx` accepts.
- The Python mixin (`project/kits/python/python.yaml`, v3 format) validates, inspects and installs Python at `sbx create` time (tested). `sbx kit pack` doesn't accept it: it requires a `spec.yaml`, an older artifact format, so the module doesn't use `pack`. Remote kits (Git or OCI) are refused unless their publisher is in `kit.allowedSources`; the module explains this rather than asking participants to change the setting.
- `sbx kit inspect sbx/copilot` reports `Policies: none`, but every Copilot sandbox gets a `kit` policy allowing Copilot's own hosts (`api.*.githubcopilot.com`, `api.github.com`, `github.com`, `copilot.github.com`). The Copilot telemetry hosts and `cafe.github.com` aren't in it, which is one reason module 01 still allows `**.githubcopilot.com` and `**.github.com`.
- The Trivy kit (`project/kits/trivy/`, a mixin adapted from [docker/sbx-kits-contrib's v3 trivy-mixin kit](https://github.com/docker/sbx-kits-contrib/tree/v3/trivy-mixin), Apache-2.0) was tested end to end with `sbx` v0.53.0: `sbx kit validate` builds it in about a minute (the Trivy download and SHA256 check pass), `sbx kit inspect` shows `Kind: mixin`, `Network: 7 allow`. Module 02 only describes the kit; module 10 adds it to the `mcp` sandbox (`--static-mcp dhi --kit ./kits/trivy copilot .`), where `trivy`, `scan-images` and `copilot` are all on the PATH and `/home/agent` stays owned by `agent`. When upstream bumps Trivy, update `TRIVY_VERSION`, both SHA256s and `provides` together.
- Like upstream, the Dockerfile builds in a first stage and keeps only the added files in a `FROM scratch` stage, which `sbx` lays over the agent's image. The kit adds two files to upstream's: `vex-repository.yaml` (Trivy's VEX Hub plus `docker-hardened-images/advisories`, as the [DHI scanning guide](https://docs.docker.com/dhi/how-to/scan/) recommends), copied to `/usr/local/share/trivy/` and copied by the script to `~/.trivy/vex/repository.yaml` on first use (the overlay doesn't write under `/home/agent`, so it can't change the home directory's ownership), and `scan-images.sh`, copied to `/usr/local/bin/scan-images`, which runs `trivy image --image-src remote --scanners vuln --vex repo` with a template that prints one line per image. Trivy downloads the VEX repositories on the first `--vex repo` scan, through `github.com`, `api.github.com`, `codeload.github.com` and `raw.githubusercontent.com`, now in the kit's rules (module 01 only covers the first three). `--table-mode summary` isn't usable with `--vex repo`: it lists every npm package of `node:22-alpine` on its own row. `--vex oci` finds no attestations for DHI images. `.gitattributes` keeps the script's LF line endings on Windows checkouts.
- Module 10's scans were tested in a fresh `mcp` sandbox created with the module's command: the first scan downloads the 134 MiB database from `mirror.gcr.io` (one attempt failed mid-download with `unexpected EOF` on a flaky connection; the retry took 24 s) and the VEX repositories. Results at the time of writing, with VEX: `python:3.12-slim` 92 (0 critical, 15 high), `dhi.io/python:3.12-alpine` 0, `node:22-alpine` 17 (7 high), `dhi.io/node:22-alpine` 0. Without VEX: 226, 0, 25 and 0. The Alpine numbers (2026-11-17, Trivy 0.70.0) were measured with the kit's helper from the host's Docker daemon (`--image-src docker`), not yet re-run inside an `mcp` sandbox; the Debian-based `dhi.io/python:3.12` then had 58 (7 high). `dhi.io/python:3.12-alpine-dev` also has 0. Docker Hub and `dhi.io` are reached through module 01's global rules, without `docker login dhi.io` (the machine was signed in to `sbx`; not checked with a fresh account). `check.trivy.dev` is blocked.
- Module 02 ends with two awareness-only sections, not run by participants: [kit sets](https://docs.docker.com/ai/sandboxes/customize/author/kit-sets/) and [environment files](https://docs.docker.com/ai/sandboxes/configuration/environment-files/). Checked with `sbx` v0.53.0 without creating a sandbox: the set descriptor's format is accepted and its `docker.io/sbx/copilot@sha256:…` component resolves (the build stops at the unpublished mixin, as expected, since set components must be published); the environment file, placed at the repository root, passes `sbx env plan` with its relative paths (sandbox, Python kit, both secrets, both ports).
- The port mixin (`project/kits/api-port/api-port.yaml`, [`port@1`](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/port%401.md)), used in module 09's "Publish a port from a kit" section, was tested end to end: `sbx kit inspect` reports `Published: 1 ports`; `sbx create` publishes the port right away on an ephemeral `127.0.0.1` host port (60020, 60021, 60022 in successive runs), which changes on every sandbox start; a pinned `sbx port publish quickstart 8000:8000` works alongside it. The spec forbids a kit from pinning the host port, so the module keeps `sbx port publish` for DevBoard, whose frontend needs `localhost:8000`. The spec's optional `name` label isn't shown by `sbx port ls`, so the kit doesn't set one. v0.54 replaced `sbx ports --publish/--unpublish` with `sbx port ls|publish|unpublish` (the old command still works, with a deprecation warning); `sbx port unpublish <SANDBOX> <SANDBOX_PORT>` removes every host mapping of that port. In the v0.54 run, the kit port landed on 60000.

## Isolation checks in module 04 (checked with `sbx` v0.53.0)

- Checked in a fresh `quickstart` sandbox (`sbx create --name quickstart --kit ./kits/python copilot .`, 22 s with cached images, 14 s of it for the Python install):
  - `env | grep _TOKEN=` shows `GH_TOKEN=proxy-managed` and `COPILOT_GITHUB_TOKEN=proxy-managed`. A `shell` sandbox shows `GH_TOKEN=gho_sbxproxymanaged000000000000000000000` instead, so the module's expected output is for Copilot sandboxes only.
  - `pwd` is the host path of the workspace; `~` is the agent's own home (`.bashrc`, `.copilot`, `.docker`, `.gitconfig`..., no `.ssh`). From a shell sandbox, the host's home folder only shows the path down to the workspace.
  - The `POST` to `paste.rs` prints `Approval required for paste.rs:443.`, then `Review and respond with: sbx policy approval ls`, and exits 0. It shows in `sbx policy log quickstart` (blocked, `No matching allow rule (default deny)`) and as a pending approval in `sbx policy approval ls`.
  - `sbx policy log <name>` also lists entries of an earlier, removed sandbox with the same name.
- Module 01: with `docker.com` allowed, `curl -I docker.com` returns `HTTP/1.1 301 Moved Permanently` with `Location: https://www.docker.com/`. Without a terminal, `sbx policy rm` needs `--force`; in a terminal it asks for confirmation.
- Pre-lab warm-up (module 00): `sbx create` of a `shell` and a `copilot` sandbox took about 7 s each with cached images, and `sbx rm` keeps the template images (`sbx template ls` unchanged). Not checked: a first download on a machine without cached images.
- Not checked: the TUI's Network panel (needs a keyboard), how far a Copilot Free allowance goes through the lab's ~10 prompts, and signing in to the DHI MCP server with a free Docker account.
- Full run of modules 00-11 on Windows 11 with `sbx` v0.54.0 (2026-11-18, PowerShell 5.1, Copilot Enterprise; agent prompts run headless with `sbx exec <name> copilot --yolo -p`, about 75 AI Credits in total): every expected output matched, apart from these. `sbx diagnose` always reported `✗ Daemon diagnostics — check timed out` with the daemon healthy (now in Troubleshooting). `ports-demo`, created with `sbx create` and no agent session, stopped about a minute after the `sbx exec` that started its web server, so module 09 now runs `sbx run --detach --name ports-demo` first; its kit port moved from 60000 to 60001 on that restart. A clone-mode sandbox whose agent has finished stops the same way, and its remote goes with it (already in the module's note). With VEX, `python:3.12-slim` had 98 vulnerabilities (15 high). Re-running `sbx mcp add dhi` when it is already registered succeeds, printing `WARN: oauth` twice. The DevBoard frontend shows the API's raw JSON validation error when you register with a reserved email domain such as `example.test`.
- The source files no longer label the intentional bugs with `# BUG:` comments, so that the agent has to find them; the tests still carry the hints.

## Full run with `sbx` v0.54.0 (Windows 11, Copilot Enterprise)

- Modules 00 to 11 ran end to end, with Copilot in prompt mode (`sbx run --name <name> -- -p "..."`) instead of interactive sessions. Not run: the TUI (module 05), and the `paste.rs` upload in module 04, which the test harness refused to send.
- Output changes: `sbx policy check network` prints a `Rule: <id>` line for allowed targets (module 01); `sbx inspect` shows `MCP mode` and `MCP servers` (module 10); Copilot names MCP tools with the gateway prefix (`mcp-gateway-dhi_get_repository`).
- Unchanged: the kit outputs (module 02), the tokens shown as `proxy-managed`, the test baseline (3 failed, 12 passed, 1 xfailed) and the final 20 passed after merging the three agents.
- Corrected later: the Python kit's `install` hosts do **not** stay in the kit policy at runtime (a `shell` sandbox lists only `pypi.org` and `files.pythonhosted.org`). The `deb.debian.org:80` and `dhi.io:80` rules in a Copilot sandbox's kit policy come from the Copilot agent, and the lab's global rules allow both hosts anyway.
- `sbx` v0.54 writes an empty `shim-start.lock` in the current folder each time the daemon starts (`sbx policy reset`, `sbx daemon restart`, or the first `sbx` command after a stop). The root `.gitignore` ignores it so that module 06's `git add -A` doesn't commit it; worth reporting upstream.
- Once, `sbx daemon restart` left the daemon unable to start (`remove ...\containerd\containerd.sock.ttrpc: The file cannot be accessed by the system.`); starting it from the user's own terminal fixed it. Not reproduced.
- Trivy counts with VEX: 83, 49, 16, 0; without: 217, 96, 24, 0.
